# Motor próprio: Fase 2 (monitor virtual)

Spec: [2026-10-30-motor-proprio-design.md](../specs/2026-10-30-motor-proprio-design.md#fase-2-monitor-virtual).

## Protótipo no GNOME Wayland (30/10/2026)

A spec dava o Wayland como "só espelha". No GNOME isso não é verdade: o Mutter cria um monitor virtual de verdade, sem nenhum diálogo, pela própria API de D-Bus (`org.gnome.Mutter.ScreenCast`, versão 4 no GNOME 51):

1. `CreateSession({})`
2. `Session.RecordVirtual({ 'cursor-mode': 1, 'is-platform': true })` devolve um stream.
3. `Session.Start()`. O stream avisa o nó do PipeWire (`PipeWireStreamAdded`).
4. **O monitor só passa a existir quando alguém consome esse nó do PipeWire**, e quem consome escolhe o tamanho na negociação do formato. No protótipo, quem consumiu foi o `gst-launch-1.0 pipewiresrc path=<nó> ! videoconvert ! video/x-raw,width=1920,height=1080 ! fakesink`.
5. O GNOME mostra o monitor como `Meta-0`, "MetaVendor / Virtual remote monitor", à direita da tela principal (x=1920). O mouse e as janelas passam para ele.
6. Ele some quando a sessão do D-Bus fecha ou quando o consumidor sai.

Captura: o Chromium continua capturando pelo portal. O seletor do GNOME lista o monitor virtual como "MetaVendor", ao lado do monitor físico. Escolhendo esse, o vídeo enviado é só a tela estendida.

O seletor aparece **uma vez por execução do app**. Ao reconectar com o mesmo processo aberto, o Chromium reaproveitou a escolha sem perguntar.

### Números (desktop → notebook, Wi-Fi, janelas se mexendo na tela estendida)

| Medida | Mediana | p95 |
|---|---|---|
| Captura até a tela | 68 ms | 185 ms |
| Recebido até a tela | 41 ms | 79 ms |
| fps (variam com o que muda na tela) | 21 | 47 |
| Ida e volta | 3 ms | 6 ms |

Nenhum pacote perdido. O codificador continuou o OpenH264, por software.

## O que falta para virar produto (Linux)

- Um consumidor do PipeWire **nosso**, no lugar do `gst-launch`: `native/linux`, em C, com libpipewire e GIO (as duas existem em todo desktop GNOME ou KDE). Ele cria o monitor no tamanho pedido, informa o conector e fica vivo até o `SIGTERM`, como o `horizonte-display` do macOS. Ele só drena os quadros: quem captura e codifica continua sendo o Chromium.
- Explicar o seletor antes de ele aparecer ("escolha a tela MetaVendor") ou, melhor, eliminá-lo. O consumidor já recebe as imagens do monitor virtual, então poderia entregá-las ao Chromium (`MediaStreamTrackGenerator`) em vez de descartá-las. Isso tira o seletor de vez, ao custo de copiar os quadros entre processos.
- KDE: a API do Mutter é só do GNOME. No KDE, o caminho é o portal com fonte `VIRTUAL`, que mostra diálogo.
- Xorg: `xrandr --setmonitor`, como hoje.
- Windows (Virtual Display Driver) e macOS (`horizonte-display`) já têm monitor virtual no app. Falta ligá-los ao motor novo, e só dá para testar com esses computadores.
